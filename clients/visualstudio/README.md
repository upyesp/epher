# Epher for Visual Studio

The epher calculator language in Visual Studio 2022 (17.x): syntax
highlighting with bracket matching, a diagnostic for every broken
statement, the answer rendered inline next to every statement that
produces one, hover with canonical signatures, completion for the
catalog, your own names, and the shared snippets, and the snippets
themselves through completion.

The extension is a thin shell (ADR-0066). All understanding lives in
`epher-lsp`, the shared language server — and the server ships inside
the extension: the vsix carries `server\epher-lsp.exe`, the
windows-x86_64 build from the same release the extension rides
(the ADR-0066 amendment that retired the downloader for Visual
Studio). No first-use network step, no cache, no version marker: an
extension update carries its matching server by construction, the
coupling the old download's version lock existed to enforce, made
physical.

If the bundled binary is somehow missing, the error is reported in an
InfoBar and editing still works through the TextMate baseline; only
the live features are missing. Reinstalling the extension restores
them.

## Supported versions

Visual Studio 2022 (17.x), Community, Professional, and Enterprise.
Older Visual Studio versions are not supported: the extension targets
the 64-bit 17.0 editor.

## Install from disk

1. Download `epher-visualstudio.vsix` from the epher release page.
2. Double-click the file: the VSIX Installer opens and installs the
   extension (this is the documented way to install a `.vsix` that is
   not on a marketplace; the Extensions > Manage Extensions dialog then
   shows the installed extension and can update or uninstall it).
3. Open or create a `.epher` file.

Visual Studio Marketplace publication comes later; the website page
and the release assets are the distribution until then.

## The features

- **Highlighting**: the shared TextMate grammar, contributed through
  the editor's TextMate repository mechanism. The baseline spelling of
  the language. Bracket matching, comment toggling, autoclosing, and
  surrounding come from the contributed language configuration.
- **Inline evaluation**: the server re-evaluates the whole file on a
  short debounce and the answers render on the statements that
  produce them.
- **Diagnostics**: parse and evaluation errors arrive as squiggles
  under the offending spans.
- **Completion**: the function catalog, your own names, and the
  shared snippets (the server embeds the snippet list, so completion
  offers them without any editor-side machinery).
- **Hover**: canonical signatures and descriptions from the catalog.

One honest limitation, verified against the Microsoft docs: Visual
Studio's in-box LSP client documents its supported LSP messages in an
explicit feature table, and semantic tokens are not among them, so the
server's semantic tokens do not color a `.epher` file here the way
they do in VS Code, Zed, and JetBrains. The TextMate grammar is the
whole visual story in Visual Studio for now.

## Run a script and see the results

The **Tools > Run Epher Script** command (also on the right-click menu
inside a `.epher` editor) evaluates the whole script and opens the
results as a tab in the editor well — the internal Visual Studio
browser frame, dockable like any document.

- Text answers and errors are anchored to their statements: every row
  carries the line it came from, and error rows render as errors.
- Every 2D and 3D graph the run produced renders inline in a Graphs
  section, as the SVGs the language server captures in memory.
- The run uses its own short-lived epher-lsp session beside the
  language-client session the editing features ride on, so a run never
  disturbs inline answers, diagnostics, or completion. The buffer text
  is sent to the run exactly as the editor shows it, saved or not.
- A run that fails (a server that cannot start, for example) reports on
  the status bar and echoes the full message to the **epher** pane of
  the Output window; statement errors also echo there as a plain-text
  transcript.

The report is written to `%TEMP%\epher\<script>.results.html` and
overwritten per run, so the file can be kept or attached after the
fact.

## The shared assets

Everything the extension knows about epher is generated from the
shared sources; never edit the copies:

- `Grammars/epher.tmLanguage` is generated from
  `clients/shared/epher.tmLanguage.json` (Visual Studio's TextMate
  engine reads the plist form, and the editor matches files by the
  grammar's declared extensions, so the generated copy carries
  `fileTypes: ["epher"]`, which the shared JSON does not need).
- `epher-language-configuration.json` ports
  `clients/vscode/language-configuration.json`, keeping the sections
  the Visual Studio Language Configuration documentation defines.

Both are regenerated by:

    python3 scripts/sync-assets.py

## Building

Requires Windows with Visual Studio 2022 and the "Visual Studio
extension development" workload (or no workload at all: the build gets
the VsSDK tooling from the `Microsoft.VSSDK.BuildTools` package):

    msbuild -restore -p:Configuration=Release clients/visualstudio/Epher.VisualStudio.csproj

The vsix lands in `bin/Release/Epher.VisualStudio.vsix`. The version
(default 0.5.52) comes from the `EpherVersion` msbuild property, which
also stamps the vsix manifest; drop the matching
`epher-lsp-windows-x86_64` binary at `server/epher-lsp.exe` before
packing (CI fetches it from the release):

    msbuild -restore -p:Configuration=Release -p:EpherVersion=0.5.41 ...

CI builds it in the `visualstudio` job of build-installers.yml and
copies the vsix to the stable asset name `epher-visualstudio.vsix`.
